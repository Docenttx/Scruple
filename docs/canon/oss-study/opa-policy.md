# OSS study: OPA/Rego, Gatekeeper, Sigstore/Kyverno attestation policy — mapped to Scruple P1–P8

**Bottom line:** OPA/Gatekeeper's real contribution isn't the Rego language, it's three structural patterns — (1) `deny[{msg, details}]` sets instead of booleans, so a policy engine returns *reasons*, not just pass/fail; (2) the ConstraintTemplate/Constraint split, which separates "what a requirement checks" from "which vendor, with what parameters, at what enforcement strength"; (3) audit-over-existing-state, which re-runs the same policy against already-admitted resources on a schedule, not just once at intake. All three are cheaply reproducible in TypeScript with Zod — none require Rego. The one thing worth stealing verbatim is OPA's bundle-signing format (a `.signatures.json` JWT hashing each file), because it's language-agnostic and solves exactly the "prove which policy version produced this pass/fail" problem. Of P1–P8, three (P1, P2, P6) are not decidable from vendor-submitted documents at all — they require observing the vendor's runtime or a third party's independent record, not a self-report; the other five become decidable *only* when the evidence itself is third-party-issued (an IdP token, a cloud KMS policy, our own witness server's countersignature) rather than the vendor describing itself. Recommendation: don't adopt Rego or CUE — implement P1–P8 as Zod refinements in TypeScript with a signed/versioned bundle borrowed from OPA's JWT format, and have Python call that evaluator rather than reimplementing the rules.

Both `open-policy-agent/opa` and `open-policy-agent/gatekeeper` are **Apache-2.0**, which carries an explicit patent grant (§3: "grants to You a... irrevocable... patent license... necessarily infringed by their Contribution(s)", with a defensive-termination clause on countersuit). Confirmed by reading `LICENSE` in both shallow clones at `/data/oss-study/opa/LICENSE` and `/data/oss-study/gatekeeper/LICENSE`.

## 1. The Rego evaluation model

### Input / data / policy triple

OPA's own philosophy doc (`docs/docs/philosophy/index.md`, "The OPA Document Model") draws the line precisely:

> "All data loaded into OPA from the outside world is referred to as **base documents**... the values generated by rules (a.k.a., decisions) are referred to as **virtual documents**... Base documents pushed synchronously are called 'input'. Policies can access these inputs under the `input` global variable."

So: **`input`** = the request-scoped document you're deciding about (submitted per-call), **`data`** = everything else the policy has loaded ahead of time (async push via `PUT /v1/data`, or async pull via the Bundle feature), **policy (Rego)** = rules that compute new (virtual) documents from `input` + `data`, referenced identically via the same `data.*` path. A decision is requested as `POST /v1/data/{path}` with a JSON body `{"input": {...}}`, and returns:

```json
{
  "decision_id": "04789f85-de5a-477b-8aa5-6d59d7742135",
  "result": true
}
```
(`docs/docs/rest-api.md:1044-1057`, real quoted example). `decision_id` exists specifically for audit logging — every decision is independently traceable even though the API itself is stateless.

### Reason, not boolean — `deny contains msg`

The canonical pattern, quoted verbatim from OPA's own Kubernetes primer (`docs/docs/kubernetes/primer.md:16-23`):

```rego
package kubernetes.admission

deny contains msg if {
    input.request.kind.kind == "Pod"
    image := input.request.object.spec.containers[_].image
    not startswith(image, "hooli.com/")
    msg := sprintf("image '%v' comes from untrusted registry", [image])
}
```

`deny` is a **set** — every rule that matches contributes one more string. This is the load-bearing idiom: instead of one `allow: bool`, you accumulate independent reasons, and the caller reports all of them at once, not just the first one hit.

### Partial evaluation

`POST /v1/compile` runs partial evaluation: give it a query plus a set of "unknowns" (defaults to `["input"]`) and it returns the *residual* conditions that still depend on data not yet supplied, rather than a boolean. Quoted table, `docs/docs/rest-api.md:1680-1684`:

| Example Query | Unknowns | Result |
|---|---|---|
| `input.x > 0` | `["input"]` | `{"result": {"queries": [[input.x > 0]]}}` — query partially evaluated, remaining conditions returned |
| `input.x > 0` | `[]` | `{"result": {}}` — false/undefined, no unknowns left to blame |
| `1 > 0` | N/A | `{"result": {"queries": [[]]}}` — always true |

This is used to push filtering logic down into a database query (e.g., turn "can this user see row X" into a SQL WHERE clause) — not directly relevant to Scruple's shape, but worth naming since it's the thing that makes OPA more than a boolean gate.

### Testing convention — `opa test`, real file quoted

OPA tests its *own* CI-trigger logic as Rego, which is a good real-world example of the test-file convention: `build/policy/pr-check/pr_check.rego` defines rules like `changes.go`, `changes.docs`; `build/policy/pr-check/pr_check_test.rego` is a sibling `_test.rego` file, same package name + `_test` suffix, that mocks `input` per-test with `with input as ...`:

```rego
package policy["pr-check_test"]
import data.policy["pr-check"] as pr_check

example_docs_changelist := [
	{"filename": "docs/docs/policy-reference/builtins/glob.mdx"},
]

test_run_docs_check_expect if {
	pr_check.changes.docs with input as example_docs_changelist
}

test_run_some_not_others_expect if {
	not pr_check.changes.docs with input as mixed_bag_changelist
	pr_check.changes.go with input as mixed_bag_changelist
}
```

Convention: `*_test.rego` file next to the policy, `test_*` function names, `with input as <fixture>` to inject a mock input document per-test (no separate mocking framework). A test can also assert a negative deliberately, with a comment explaining *why* — e.g. `test_run_no_proto_check_for_stray_proto` documents that a `.proto` outside `buf.yaml`'s modules must **not** trigger the proto-check job, "because buf would silently ignore it and we'd ship false-green."

### Bundles — how policy is distributed to a running system

`docs/docs/management-bundles/index.md`. A bundle is a gzipped tarball of Rego + JSON data, pulled by a running OPA instance on a poll interval, or provided at startup with `--bundle`. Multiple bundles can be combined; delta bundles exist for incremental updates (but "Delta bundles do not support bundle signing" — noted explicitly, line 727). This is directly relevant to §4 below.

## 2. Gatekeeper's ConstraintTemplate / Constraint split

This is the piece closest to Scruple's actual shape: **one reusable requirement definition, many parameterized instances.**

### ConstraintTemplate — the reusable requirement

Real file, `example/templates/k8srequiredlabels_template.yaml`:

```yaml
apiVersion: templates.gatekeeper.sh/v1
kind: ConstraintTemplate
metadata:
  name: k8srequiredlabels
spec:
  crd:
    spec:
      names:
        kind: K8sRequiredLabels
      validation:
        # Schema for the `parameters` field
        openAPIV3Schema:
          type: object
          properties:
            labels:
              type: array
              items:
                type: string
  targets:
    - target: admission.k8s.gatekeeper.sh
      rego: |
        package k8srequiredlabels

        violation[{"msg": msg, "details": {"missing_labels": missing}}] {
          provided := {label | input.review.object.metadata.labels[label]}
          required := {label | label := input.parameters.labels[_]}
          missing := required - provided
          count(missing) > 0
          msg := sprintf("you must provide labels: %v", [missing])
        }
```

Two things worth noting structurally: (a) the template declares its own **parameter schema** (`openAPIV3Schema` under `crd.spec.validation`) — the requirement author decides what a caller is *allowed* to configure, not the caller; (b) the violation message carries a **structured `details`** payload (`missing_labels`), not just prose — this is `deny[{msg, details}]`, the machine-checkable-reason pattern one level further than OPA's plain `deny contains msg`. `applying this template registers a new CRD kind (`K8sRequiredLabels`) that constraints instantiate.

### Constraint — the per-target instantiation

Real file, `example/constraints/all_pod_must_have_gatekeeper_namespaceselector.yaml`:

```yaml
apiVersion: constraints.gatekeeper.sh/v1beta1
kind: K8sRequiredLabels
metadata:
  name: pod-must-have-gk
spec:
  match:
    kinds:
      - apiGroups: [""]
        kinds: ["Pod"]
    namespaceSelector:
      matchExpressions:
      - key: workloadtype
        operator: In
        values: [prodworkload]
  parameters:
    labels: ["gatekeeper"]
```

`match` narrows *scope* (which resources this instance applies to); `parameters` fills the template's schema (which labels, in this case). Template = policy logic + parameter contract, authored once. Constraint = scope + parameter values, authored per-deployment/team/environment.

### Violations surfaced and audited over existing state — not just at admission

Gatekeeper runs a periodic **audit** loop independent of the admission webhook, re-checking resources that already exist in the cluster (`website/docs/audit.md`): "Audit performs periodic evaluations of existing resources against constraints, detecting pre-existing misconfigurations." Results land in the constraint's own `status.violations` field:

```yaml
status:
  auditTimestamp: "2019-05-11T01:46:13Z"
  enforced: true
  violations:
  - enforcementAction: deny
    group: ""
    version: v1
    kind: Namespace
    message: 'you must provide labels: {"gatekeeper"}'
```

This matters because admission-time checking only catches things at the moment of creation; audit re-derives compliance state on a schedule, so a requirement that starts failing later (an expired cert, a config drift) is caught without a new admission event.

### Enforcement actions — deny / dryrun / warn

`website/docs/violations.md`, quoted: `enforcementAction: dryrun` — "enables constraints to be deployed in the cluster without making actual changes... impacted resources are surfaced as violations in the `status` field." `enforcementAction: warn` — "offers the same benefits as dry run... will also provide immediate feedback" at the point of the `kubectl apply` itself:

```
$ kubectl apply pod.yaml
Warning: [prod-repo-is-openpolicyagent] container <nginx> has an invalid image repo <nginx>, allowed repos are ["openpolicyagent"]
pod/pause created
```

Default is `deny`. The stated use case for `dryrun` is explicitly "rolling out new constraints to running clusters" — i.e., a brand-new or newly-tightened requirement launches non-blocking, then gets flipped to `deny` once its false-positive rate is known. `enforcementAction: scoped` + `scopedEnforcementActions` lets an operator set a *different* action per enforcement point (admission vs. audit vs. VAP-generated policy) for the same constraint (`website/docs/enforcement-points.md`).

## 3. Attestation verification — Sigstore policy-controller and Kyverno

Both express the same shape: *this artifact must carry an attestation of predicate type T, signed by identity I, whose content satisfies condition C.* This is structurally the closest thing in the OSS landscape to a Scruple P-requirement.

### Kyverno — `verifyImages[].attestations[]`

Fetched from the live Kyverno policy library (`kyverno.io/policies/other/verify-image-slsa/`), a complete real `ClusterPolicy`:

```yaml
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: verify-slsa-provenance-keyless
spec:
  validationFailureAction: Audit
  webhookTimeoutSeconds: 30
  rules:
    - name: check-slsa-keyless
      match:
        any:
          - resources:
              kinds:
                - Pod
      verifyImages:
        - imageReferences:
            - myreg.org/path/repo:*
          attestations:
            - predicateType: https://slsa.dev/provenance/v0.2
              attestors:
                - count: 1
                  entries:
                    - keyless:
                        subject: https://github.com/slsa-framework/slsa-github-generator/.github/workflows/generator_container_slsa3.yml@refs/tags/v*
                        issuer: https://token.actions.githubusercontent.com
                        rekor:
                          url: https://rekor.sigstore.dev
              conditions:
                - all:
                    - key: "{{ regex_match('^https://github.com/slsa-framework/slsa-github-generator/.github/workflows/generator_container_slsa3.yml@refs/tags/v[0-9].[0-9].[0-9]$','{{ builder.id}}') }}"
                      operator: Equals
                      value: true
```

`validationFailureAction: Audit` is Kyverno's version of Gatekeeper's `dryrun` (the other value is `Enforce`, Gatekeeper's `deny`). The `attestors[].keyless.{issuer,subject}` pair is identity, not a static key — this is the same "who signed it" check as P4/P8. `conditions` is where predicate-*content* gets checked (here, a regex over `builder.id` inside the SLSA predicate) — this is the piece that goes beyond "is it signed" into "does the signed claim actually say what we need it to say."

### Sigstore policy-controller — `ClusterImagePolicy`, and it embeds Rego directly

Fetched from `docs.sigstore.dev/policy-controller/overview/`:

```yaml
apiVersion: policy.sigstore.dev/v1beta1
kind: ClusterImagePolicy
metadata:
  name: image-policy-keyless-with-attestations
spec:
  images:
  - glob: registry.local:5000/policy-controller/demo*
  authorities:
  - name: verify custom attestation
    keyless:
      url: http://fulcio.fulcio-system.svc
      identities:
      - issuerRegExp: .*kubernetes.default.*
        subjectRegExp: .*kubernetes.io/namespaces/default/serviceaccounts/default
    ctlog:
      url: http://rekor.rekor-system.svc
    attestations:
    - name: custom-match-predicate
      predicateType: https://cosign.sigstore.dev/attestation/v1
      policy:
        type: cue
        data: |
          predicateType: "https://cosign.sigstore.dev/attestation/v1"
          predicate: "foobar e2e test"
```

Notable: `policy.type` accepts **`cue` or `rego`** — policy-controller lets the predicate-content check itself be written in either language, evaluated against the already-verified (signature-checked) attestation payload. This confirms Rego's natural niche: checking a document's *content* once you already trust its provenance, not establishing that provenance itself (which is Fulcio/Rekor's job, cryptographic, not policy-engine work).

## 4. Policy as a distributable, signed, versioned artifact

OPA is the one of the four that actually does this (Gatekeeper distributes policy as Kubernetes CRDs applied via the API server / GitOps, which relies on the *cluster's* RBAC and audit log, not a bundle signature scheme of its own).

From `docs/docs/management-bundles/index.md:474-616` (quoted):

> "When OPA receives a new bundle, it checks that it has been properly signed using a (public) key that OPA has been configured with out-of-band. Only if that verification succeeds does OPA activate the new bundle; otherwise, OPA continues using its existing bundle and reports an activation failure via the status API and error logging."

Mechanism: a signed bundle (gzipped tarball) contains an extra `.signatures.json` — an array of JWTs. Real quoted example:

```json
{
  "signatures": [
    "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJmaWxlcyI6W3sibmFtZSI6Ii5tYW5pZmVzdCIsImhhc2giOiJjMjEzMTU0NGM3MTZhMjVhNWUzMWY1MDQzMDBmNTI0MGU4MjM1Y2FkYjlhNTdmMGJkMWI2ZjRiZDc0YjI2NjEyIiwiYWxnb3JpdGhtIjoiU0hBMjU2In0..."
  ]
}
```

decoding to a JWT payload of the form:

```json
{
  "files": [
    {"name": ".manifest", "hash": "c213...", "algorithm": "SHA-256"},
    {"name": "roles/bindings/data.json", "hash": "42cf...", "algorithm": "SHA-256"}
  ]
}
```

Verification (quoted, condensed): "Verify the JWT signature with the appropriate public key; verify that the JWT payload and target directory specify the same set of files; verify the content of each file by checking the hash recorded in the JWT payload is the same as the hash generated for that file." Structured (JSON/YAML) files get a specific canonicalization step before hashing: *"read the byte stream and parse into a JSON structure; then recursively order the fields of all objects alphabetically and then apply the hash function to the result"* — solving exactly the "whitespace/key-order shouldn't change the hash" problem any signed-JSON scheme runs into. Optional claims `scope`/`iat`/`iss` are settable via `--claims-file`; `scope` is verified against an out-of-band value if supplied, `iat`/`iss` are informational only.

This entire mechanism is **language-agnostic** — JWT + per-file SHA-256 + a canonicalization rule for JSON. Nothing about it depends on Rego or the OPA runtime. It is the one piece of this study directly reusable as-is (via `jose`/`jsonwebtoken` in TS, `pyjwt`/`cryptography` in Python) without adopting anything else from OPA.

## 5. Mapping to Scruple

### 5a. P1, P3, P5 as executable Rego (the concrete artifact)

Invented but plausible input shapes for a Scruple **baseline manifest** (what a vendor submits describing its integration) and a **witness leaf** (the append-only chain of witnessed events):

```json
// baseline_manifest.json — submitted by the vendor, describes their capture-path config
{
  "vendor_id": "runpod",
  "capture_path": {
    "component": "training-callback-hook",
    "deployed_from": {
      "artifact_digest": "sha256:1234abcd...",
      "repo": "github.com/runpod/witness-hook",
      "build_provenance": "https://slsa.dev/provenance/v1"
    },
    "writable_by": ["ci-pipeline-svc"],
    "reachable_by_witnessed_party": false
  },
  "signing": {
    "key_custody": "kms",
    "kms_arn": "arn:aws:kms:us-east-1:0000:key/abc-123",
    "key_reachable_by": []
  },
  "declared_attestation_mode": "verified"
}
```

```json
// witness_leaf.json — one entry in the append-only event chain
{
  "leaves": [
    {
      "seq": 4820,
      "prev_leaf_hash": "sha256:8f2a...",
      "principal": {"id": "user:alice@acme.com", "auth_method": "oidc", "idp": "https://accounts.acme.com"},
      "event": {"type": "training_step_capture", "capture_component_hash": "sha256:1234abcd..."},
      "content_posture": "zero-content",
      "signature": {"alg": "ES256", "kid": "witness-signer-2026", "sig": "MEUCIQ..."}
    },
    {
      "seq": 4821,
      "prev_leaf_hash": "sha256:<hash of seq 4820>",
      "principal": {"id": "user:alice@acme.com", "auth_method": "oidc", "idp": "https://accounts.acme.com"},
      "event": {"type": "training_step_capture", "capture_component_hash": "sha256:1234abcd..."},
      "content_posture": "zero-content",
      "signature": {"alg": "ES256", "kid": "witness-signer-2026", "sig": "MEUCIB..."}
    }
  ]
}
```

**P1 — runtime boundary integrity**, following Gatekeeper's `deny[{msg, details}]` idiom directly:

```rego
package scruple.p1

deny contains {"code": "P1_REACHABLE", "msg": msg} if {
    input.capture_path.reachable_by_witnessed_party == true
    msg := sprintf(
        "capture path component %q is reachable by the witnessed party; P1 requires the capture code sit outside their write boundary",
        [input.capture_path.component],
    )
}

deny contains {"code": "P1_SELF_WRITABLE", "msg": msg} if {
    some principal in input.capture_path.writable_by
    principal == input.vendor_id
    msg := sprintf(
        "capture path is writable by the vendor's own principal %q; P1 requires it be outside vendor write access",
        [principal],
    )
}

deny contains {"code": "P1_NO_PROVENANCE", "msg": "capture path artifact declares no build provenance; P1 cannot be evaluated without a verifiable build/deploy record"} if {
    not input.capture_path.deployed_from.build_provenance
}
```

**P3 — API key custody**:

```rego
package scruple.p3

approved_custody := {"kms", "hsm"}

deny contains {"code": "P3_CUSTODY", "msg": msg} if {
    not input.signing.key_custody in approved_custody
    msg := sprintf(
        "signing key custody %q is not in the approved set %v; P3 requires the signing key be unreachable by the witnessed party",
        [input.signing.key_custody, approved_custody],
    )
}

deny contains {"code": "P3_REACHABLE", "msg": msg} if {
    some principal in input.signing.key_reachable_by
    principal == input.vendor_id
    msg := sprintf("signing key is reachable by vendor principal %q", [principal])
}

deny contains {"code": "P3_NO_ARN", "msg": "custody class is kms but no kms_arn is declared; custody claim cannot be checked"} if {
    input.signing.key_custody == "kms"
    not input.signing.kms_arn
}
```

**P5 — immutable event chain** (input is the `leaves` array, evaluated across the whole chain, not one leaf at a time):

```rego
package scruple.p5

deny contains {"code": "P5_CHAIN_BREAK", "msg": msg} if {
    some i
    i > 0
    leaf := input.leaves[i]
    prev := input.leaves[i - 1]
    expected := sprintf("sha256:%s", [crypto.sha256(json.marshal(prev))])
    leaf.prev_leaf_hash != expected
    msg := sprintf("leaf seq=%d does not chain from leaf seq=%d (hash mismatch)", [leaf.seq, prev.seq])
}

deny contains {"code": "P5_SEQ_GAP", "msg": msg} if {
    some i
    i > 0
    leaf := input.leaves[i]
    prev := input.leaves[i - 1]
    leaf.seq != prev.seq + 1
    msg := sprintf("sequence gap: leaf %d followed by leaf %d, expected %d", [prev.seq, leaf.seq, prev.seq + 1])
}

deny contains {"code": "P5_UNSIGNED", "msg": msg} if {
    some leaf in input.leaves
    not leaf.signature.sig
    msg := sprintf("leaf seq=%d carries no signature", [leaf.seq])
}
```

Honest caveat on P5: `crypto.sha256(json.marshal(x))` is order-sensitive to JSON key ordering the way OPA's own bundle hashing is — which is exactly why OPA's bundle spec adds the "recursively order fields alphabetically before hashing" rule quoted in §4. Any real implementation of P5 needs that same canonicalization step, in whatever language it's written. Separately: Rego (and this policy) can check *chain structure* — hash linkage, sequence contiguity, a signature field being present — but it cannot itself verify that `signature.sig` is a valid ES256 signature over the leaf content unless the leaf is JWT-shaped (OPA has `io.jwt.verify_es256`, not a generic detached-signature verifier). Structural chain-integrity and cryptographic signature validity are two different checks; only the first is naturally a "policy" question.

### 5b. P1–P8: decidable from submitted data, or does it require observing the vendor's runtime?

The general trap: a policy engine evaluates a *document*. If the document is the vendor describing itself, the policy checks self-consistency of the vendor's story, not truth. The pattern that actually escapes the trap, visible in every OSS example above, is: **never evaluate a claim the subject made about itself — evaluate an artifact a third party issued about the subject** (Fulcio/an IdP issuing the identity token, Rekor recording the signature, AWS enforcing the KMS policy, our own witness server countersigning the chain). That's the same move Sigstore/Kyverno make: they never trust the image's self-description, they trust Fulcio's signed identity claim about who built it.

| # | Requirement | Reachable from vendor-submitted document? | Why |
|---|---|---|---|
| P1 | Runtime boundary integrity | **No.** | A document can *declare* `reachable_by_witnessed_party: false`, but proving no other write path exists to the capture code requires observing the vendor's actual deployment (or an independent SLSA/provenance attestation from the vendor's build system — itself a third party record, not the vendor's own claim). A self-reported boolean is unfalsifiable from the document alone. |
| P2 | Baseline coverage of the capture path | **No.** | Whether the declared capture path covers 100% of the real code path that touches witnessed data is a runtime/dataflow fact, not something a manifest can prove about itself. |
| P3 | API key custody | **Partially — reachable if the evidence is the KMS/HSM policy document itself**, not the vendor's claim about it. | A `kms_arn` plus the actual IAM/KMS resource policy (fetched independently, or submitted but cryptographically tied to the cloud provider's control plane) is a third-party-enforced fact. A bare `"key_custody": "kms"` string is just an assertion. |
| P4 | Principal identity | **Yes**, if identity comes from a verifiable OIDC/JWT token from an IdP (same shape as Sigstore's `issuerRegExp`/`subjectRegExp`). | The token, not the vendor, is the source of truth. |
| P5 | Immutable event chain | **Yes, structurally** — chain linkage, sequence gaps, and signature *presence* are pure document checks (shown in §5a). Signature *validity* is decidable only if the leaves are independently verifiable (signed by Scruple's own witness key, not the vendor). | Self-reported "our chain is immutable" is not; a chain we ourselves countersigned is. |
| P6 | Zero-content posture | **No.** | `"content_posture": "zero-content"` is exactly the vendor's own claim about what it sent. The policy can check the leaf doesn't *contain* an obviously prohibited field, but it cannot prove the vendor's runtime didn't emit content through some other channel outside the witnessed leaf. This is the same class of problem as P1/P2 — internal to the vendor's boundary, invisible to a submitted document. |
| P7 | Attestation declaration (verified vs. passthrough) | **Yes.** | This is a declared enum on a document — exactly what a policy engine is good at (`declared_attestation_mode in {"verified","passthrough"}`). Whether the *declaration itself* is honest is P8's problem, not P7's. |
| P8 | Attestation import discipline | **Yes, if** the imported attestation carries its own independently-verifiable signature (issuer + subject, Rekor-style transparency log entry, or equivalent). | This is the strongest structural parallel to Sigstore/Kyverno's `attestors[].keyless.{issuer,subject}` — decidable exactly because the thing being checked is someone else's signature, not the vendor's self-report. |

Net: **P1, P2, P6 are not reachable this way** — they are genuinely runtime-boundary facts and no document-checking scheme (Rego, CUE, Zod, or otherwise) changes that; they need either direct runtime attestation (an eBPF/hardware witness, a signed SLSA provenance record from the vendor's own build system, or an audit/pen-test) or they stay judgment calls a human makes at onboarding. P3, P4, P5, P7, P8 become genuinely decidable *only* once the source document is swapped from "vendor's claim" to "third party's record" — the policy engine choice doesn't fix this, the evidence-sourcing does.

### 5c. Is Rego worth the runtime cost?

**No — steal the pattern, not the engine.** Three structural pieces are cheap to reproduce natively and don't require a new runtime at all:

- **Structured deny reasons** (`deny contains {code, msg, details}`): trivial in Zod via `.superRefine((doc, ctx) => { ... ctx.addIssue({code, message, path}) ... })`, one refinement function per P-requirement, returning every violation in one pass instead of failing fast on the first.
- **Signed, versioned policy bundle**: OPA's `.signatures.json` JWT format (§4) is language-agnostic — implement it directly with `jose` (TS) / `pyjwt` (Python): hash each rule-file (canonicalized JSON, alphabetized keys — the exact rule OPA already worked out), wrap the file list + hashes in a JWT, sign with a key Scruple controls. This gets us "prove which P1–P8 version produced this pass/fail" without adopting anything else.
- **ConstraintTemplate/Constraint split**: see §5d — this is a data-modeling decision, not a language decision.

What Rego (or CUE, which Sigstore policy-controller also supports natively, per §3) would actually buy over Zod: a declarative, evaluatable-without-executing-arbitrary-code policy that could, in principle, be handed to *someone else's* runtime to run against evidence they hold locally, plus native partial-evaluation/set-algebra (Gatekeeper's `missing := required - provided` reads naturally in Rego, awkwardly in Zod). But re-read our actual architecture: **Scruple's own witness server is the evaluator.** The vendor calls us; we hold P1–P8; we check evidence they submit (or that a third party issued about them). We are never in OPA/Gatekeeper/policy-controller's actual bind — handing a policy bundle to a runtime we don't control, on infrastructure an adversary administers. That's the scenario bundle-signing and portable-DSLs are built for, and it's not our scenario. So the strongest argument for Rego (portability to an untrusted host) doesn't apply here; the requirement set (eight checks, mostly boolean/set logic over a known JSON shape) doesn't need Rego's evaluation model to be legible; and the cost (a new runtime, a WASM or Go dependency, no Python-native execution, a team member has to learn Rego to touch P1–P8) is real and ongoing. Verdict: implement natively in TypeScript.

Alternatives considered:

- **JSON Schema** — good for shape/type/required-field/enum validation (a meaningful slice of P7, parts of P3), but weak for cross-document logic: set differences (P1's writable-by-check), chain-linkage-across-array-elements (P5), or "the reason this failed" as a first-class structured object rather than a validator-generated error path. You'd end up hand-rolling a reason layer on top anyway — at which point you've built half of what Zod gives natively.
- **CUE** — the best non-Rego fit; it's already the sibling option to Rego inside Sigstore policy-controller's own `policy.type` field, and it's a smaller, dependency-light single binary (no server, no bundle-fetch loop). But it's still a language we don't run today, with the same two-implementation risk across TS/Python that Rego has, for a use case (portable-to-an-untrusted-host policy) we've just established we don't have. Keep it in mind as the next step up if the check set grows to something genuinely declarative/config-shaped rather than the current mostly-boolean checks — don't adopt it now.
- **Zod (recommended)** — native to the TS side already in use, type-checked at the source, ergonomic `.superRefine` for the `deny[{code,msg}]` idiom, zero new runtime. The real cost is the TS/Python split: Zod has no Python equivalent (Pydantic is closest but is a *second* implementation of the same eight rules — precisely the "prose drifts across files" problem this whole exercise exists to kill). Fix: keep P1–P8 canonical in one place (a small Node service or CLI the evaluator lives in) and have any Python caller invoke it rather than re-encoding the rules in Pydantic.

### 5d. ConstraintTemplate/Constraint mapped to "P-requirement" vs. "this vendor's integration"

The mapping is close to exact:

- **ConstraintTemplate ≈ a P-requirement definition.** Authored once by Scruple, not per-vendor: "what does a P3 check need as parameters" (e.g. the approved custody-class set, `{"kms","hsm"}`), expressed the way Gatekeeper's template declares an `openAPIV3Schema` for its `parameters` field. This is the requirement author (Scruple) deciding the shape of what a vendor is allowed to configure — not the vendor.
- **Constraint ≈ a specific vendor's instantiation**, with `parameters` filled in (RunPod's actual `kms_arn`, its actual `writable_by` list) and a `match`-equivalent scope (which of the vendor's environments/integrations this applies to — e.g. only their production capture path, not a sandbox).
- **enforcementAction (deny/dryrun/warn) ≈ Scruple's rollout story for a requirement or a vendor.** A brand-new P-requirement, or a newly-onboarded vendor, should launch in `dryrun`: violations visible in a status/report, nothing blocked — exactly Gatekeeper's stated use case, "rolling out new constraints to running clusters" without breaking things day one. Flip to `deny` once the false-positive rate on real vendor evidence is known.
- **Audit-over-existing-state ≈ re-evaluating already-onboarded vendors on a schedule, not just at signup.** A vendor that passed P5 six months ago can start failing it today if, e.g., the hash-chain convention tightens or a KMS policy silently drifted. Gatekeeper's separation of "admission-time check" from "periodic audit of what's already there" is directly the separation Scruple needs between "check this at integration review" and "re-check every onboarded vendor weekly against the current P1–P8 bundle version," surfacing drift the way Gatekeeper surfaces `status.violations` on a constraint.
- **`violation[{"msg":..., "details":...}]` ≈ the `deny[{code, msg}]` shape already drafted in §5a** — same idiom, one level more structured than OPA's plain `deny contains msg` because `details` carries machine-usable data (Gatekeeper's `missing_labels` list ≈ our `P1_SELF_WRITABLE`'s offending principal).

The one place the mapping *doesn't* transfer cleanly: Gatekeeper's ConstraintTemplate ships its Rego straight into the cluster it controls (a CRD applied via `kubectl`/GitOps, validated by Gatekeeper's own webhook running in that same cluster). Scruple's "ConstraintTemplate" never leaves our boundary — the vendor never runs it, we do, against evidence they or a third party hand us. So the template/constraint split is worth keeping; the *distribution* mechanism (a CRD applied to someone else's cluster) is not something we need to reproduce.
