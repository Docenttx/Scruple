**Status:** Analysis and specification. **Nothing was implemented, edited, or committed.**

## Headline

The premise is confirmed. `grep -rn -i "c2pa|signasset|watermark" lib/canvas/ app/canvas-proxy/ modal/` exits 1 — **zero matches**. Studio has never produced a C2PA manifest and there is no code path from Studio to the signer.

Three things I found that change the shape of the work, and I will state them before the specification because two of them contradict assumptions in the question:

**1. The C2PA signing path is not merely unreached from Studio — it is currently broken for every caller.** `lib/c2pa/signAsset.ts:20` names the dev private key `services/c2pa-signer/keys/es256.pem`. That file does not exist on this host and is gitignored (`services/c2pa-signer/keys/.gitignore:4`). `signAsset()` checks it at line 303 and returns `{ok:false, error:'signer cert/key missing at services/c2pa-signer/keys/'}` before spawning Python. A working dev pair *does* exist — `keys/signer.pem` + `keys/signer.key`, verified to match (identical public-key MD5), and `keys/regen-dev-cert.sh:5-6` says those are the files it produces. The emitter points at the wrong pair. I signed a real, `validation_state: Valid` manifest in memory with `signer.pem`/`signer.key` and the current Studio-shaped assertion set; the same run with `es256.pub` fails with `COSE signature invalid`, which is what a missing private key looks like from c2pa-rs.

**2. There is no remote signer, and `asset_path` is a path on the *app* host.** `lib/c2pa/signAsset.ts:320-323` spawns `python3 services/c2pa-signer/sign.py` as a subprocess of the Next.js process. There is no HTTP server anywhere in `services/c2pa-signer/` (`grep -n "HTTPServer|flask|fastapi|uvicorn|listen" services/c2pa-signer/*.py` → nothing). The `:8443` signer daemon exists only in Terraform (`deploy/oci-signer-rotation/terraform/instance-pool.tf:43-47`) and in a runbook that documents a multipart `-F content=@…` API (`docs/c2pa-conformance-evidence/2026-07-30/security-architecture/runbooks/bootstrap/oci-console-walkthrough.md:620-650`) which the route does not implement. `SCRUPLE_C2PA_SIGNER_URL` appears in two doc files and in **zero** lines of code.

**3. Studio does not capture what the merge doc says it captures — not on the proxy path.** This one matters most for question 3.

| Claim in `STUDIO_L2_MERGE.md` | On the canvas-proxy path | Where it actually is |
|---|---|---|
| full ComfyUI workflow graph | **YES** | `lib/canvas/witness.ts:97-102` → `ingest.ts:206-207` → `workflow_hash` |
| dual model fingerprints | **NO** | `captureOutput` (`lib/canvas/witness.ts:126-144`) never passes `modelFingerprints`. Only `lib/runs/execute.ts:94,261` does — the `/api/generate` + CC-dev path, which does not go through ComfyUI-in-the-browser |
| container manifest with real git SHAs | **NO — nowhere in the estate** | `modal/container_manifest.py` computes it, `scruple_runner.py:674-677` returns it, `lib/compute/modal.ts:125-126` parses it, and **no `ingestIteration` call site passes `containerMachineManifestHash`**. `grep -rn containerMachineManifest --include=*.ts` hits only the type declarations and the parse. It is dropped |

What Studio's leaf actually carries for toolchain is `machines.manifest_hash` (`lib/canvas/witness.ts:115-123`) — the hash of the **declarative** descriptor, in which every `commit_sha` is `null` and three of six packs pin the mutable ref `main` (`config/default-machine-manifest.json`). `lib/canvas/manifest.ts:24-25` says so in the type: *"Resolved commit sha (40 hex). null until the build worker resolves it."*

So the strongest provenance claim available to a Studio C2PA manifest today is **workflow graph + declarative toolchain descriptor**. The dual fingerprints and the real-SHA container manifest are one small plumbing change away, and that change is a prerequisite for the assertion I recommend in §3 — not an optional extra.

## 1. The existing C2PA signing path, end to end

### 1c. `services/c2pa-signer/sign.py`

Reads the job from stdin (65-80), then in order:

1. **123-130 — age guard.** `age_guard_verdict()` refuses if the CVM is older than `SCRUPLE_SIGNER_MAX_AGE_DAYS` (default 60).
2. **138-145 — OS patch-recency guard.** Refuses if the last package install is > 90 days old; fail-closed in production, permissive in dev.
3. **160-178 — c2pa settings.** `builder.created_assertion_labels` for the four SDK labels; `verify.*` relaxed only when `SCRUPLE_C2PA_DEV == "1"` exactly.
4. **187-192** — `c2pa.Signer.from_callback(vault_sign_es256, ES256, cert_str, tsa_url)`.
5. **202-210** — rewrites `claim_generator` to append the *real* installed SDK version. On this host that is **c2pa-python 0.36.0**, not the "0.89" the module docstrings still claim throughout (`sign.py:42,48-53`; `signAsset.ts:184`).
6. **219-232 — assertion partition.** Fail-closed; see §3.
7. **239-242** — appends `ai.scruple.signer-runtime.v1` when IMDS is reachable *and* the host is judged a production signer.
8. **254-276** — `Builder`, `set_intent(intent, dst)`, `add_action(...)`.
9. **288-290** — stream sign with the caller-declared MIME (deliberately, to dodge `sign_file`'s `.flac`/`.jxl` extension bugs).
10. **292-302** — result includes `signing_mode`, `signer_identity`, both guard verdicts and the partition audit. Note `signAsset.ts:338-346` parses only a subset; the guard verdicts and partition audit are discarded by the Node side.

### 1d. `services/c2pa-signer/vault_sign.py`

Two modes on one callback signature (97-105), dispatched purely on `SCRUPLE_C2PA_VAULT_KEY_OCID`:

- **Local (36-52):** loads `SCRUPLE_C2PA_LOCAL_KEY_PATH` (default `keys/es256.pem`), signs with `cryptography`, returns raw R‖S.
- **Vault (55-91):** lazy-imports `oci`, builds `InstancePrincipalsSecurityTokenSigner()` (line 71), calls `KmsCryptoClient.sign` with `messageType="RAW"`, `ECDSA_SHA_256`, then DER→raw.

### 1e. What it needs from a caller — the complete list

1. **An absolute filesystem path readable by the Node process**, to a regular file (route 147-153, `signAsset` 295).
2. **A `project_id` owned by the authenticated user**, and a project row satisfying the tier's precondition.
3. **A MIME the signer supports** — derived from the file *extension* (`mimeFromPath`), never from bytes or from `output_content_type`.
4. **`product` ∈ {studio, fusion}** — this is the only switch selecting `ai.scruple.workflow` vs `ai.scruple.cad`.
5. **A `tier`** — which decides whether `ai.scruple.provenance` is emitted at all.
6. **Nothing else.** No bytes, no storage handle, no content hash, no leaf reference. The caller supplies a path and a database key; everything else is read server-side.

**And three things it needs from the environment that are not currently satisfied on this host:**

- A private key at `keys/es256.pem` (absent — see Headline 1).
- An age guard that does not refuse. On this machine `age_guard_verdict()` returns `refuse: true` the moment `SCRUPLE_C2PA_VAULT_KEY_OCID` is set, because `_is_production_signer()` (`signer_runtime.py:103-107`) treats a set OCID as proof of being a CVM, IMDS at `169.254.169.254` answers (this *is* an OCI host), and the app-tier instance is 147.44 days old against a 60-day maximum. Measured, not inferred.
- The `oci` Python SDK, if vault mode is used. It is **not installed** (`ModuleNotFoundError: No module named 'oci'`).

## 2. How should a Studio asset reach the signer?

### 2a. Where Studio's bytes actually are

Three copies exist at the moment `captureOutput` finishes:

| Copy | Location | Lifetime |
|---|---|---|
| Modal container | ComfyUI's `output/` dir inside the per-user container | container lifetime |
| Object storage | user's Drive at `iterations/<hash12>.<ext>` — `ingest.ts:228-243` | permanent, per-user OAuth |
| App host | `artifacts/<hash[0:2]>/<hash>` — `ingest.ts:247`, `lib/scruple/artifacts.ts:18-24` | *nominally* short-term |

`ingest.ts:5-7` and `244-246` describe a "retention sweeper" that "purges these after the storage upload is confirmed (Pivot S12)". **There is no sweeper.** Nothing in `lib/`, `scripts/` or `app/` implements it. So today the local content-addressed copy is permanent, and `artifactPath(output_hash)` is a valid `asset_path` for the existing route without any change at all.

That is the trap. It works *because* the signer is a subprocess of the web app, and it stops working the instant the L2 architecture the whole programme is built around actually exists.

### 2b. The three options

**Option A — bytes over HTTP.** Caller POSTs the asset body to the signer; signer returns the signed bytes.

*For.* It is the only option that survives the signer becoming a separate, network-isolated CVM — which is the entire point of `L2_FLOOR.md` H-1 and of the Terraform in `deploy/oci-signer-rotation/`. It is what the runbook already documents (`-F content=@…`). It is what `components/LockButtons.tsx:84-86` names as the first of two blockers on enabling the C2PA button: *"takes bytes or a handle rather than an asset_path on the signer host (a desktop client cannot supply one)"*. It requires the signer to hold no storage credentials, which keeps C.2.2 custody narrow. And it makes the desktop plugins reachable by the same endpoint, which no other option does.

*Against.* Video. Studio produces `.mp4`/`.webm` through `SaveVideo`/`SaveWEBM` (`scruple_runner.py` classifies these at the video branch), and a LoRA training run returns a `.safetensors` that can be hundreds of megabytes. Round-tripping those through Next.js twice is real cost. It is bounded, though: C2PA signing is a publication-time act on selected assets, not a per-generation act on every preview.

**Option B — a storage handle the signer resolves.** Caller passes `{provider, fileId}`; the signer calls Drive.

*For.* No bytes on the wire twice.

*Against, decisively.* It puts the user's Drive OAuth token inside the Signer TOE. `lib/storage/types.ts:33-57` shows `readFile(userId, pointer)` is per-user credentialed; `lib/storage/dispatch.ts:11-15` shows Drive is the only implemented provider. The GPSA's whole argument for the signer is that it holds one key and nothing else. Handing it a per-user credential store to satisfy a bandwidth concern trades a C.2.2 property for a performance property. It also makes the signer's failure modes include *the user's Drive quota*, and it cannot serve the desktop plugins at all, since a Fusion user's file has no Scruple storage pointer.

There is a narrower variant worth naming and also rejecting: pass a **Scruple** handle — `{content_hash}` — and let the signer fetch `GET /api/artifact/<hash>`. That avoids the OAuth problem but inverts the trust direction (the signer becomes a client of the app tier it is supposed to be isolated from) and reintroduces the same bytes-over-HTTP cost with an extra hop. It is Option A with a worse topology.

**Option C — a shared volume.** Both hosts mount the same filesystem.

*For.* Zero-copy. It is effectively what happens today by accident.

*Against.* It is the single change most corrosive to the L2 story. `L2_FLOOR.md` §3 row C.2.6 already grades the witness **FAILS** for "shares a host with the web app; compromise of the app tier yields the witness secret." A shared mount reintroduces exactly that adjacency for the signer, deliberately, after the estate spent the programme removing it. It also cannot cross the Modal boundary or reach a desktop plugin.

### 2c. Recommendation

**Option A — bytes over HTTP — with a same-process fast path that is an optimisation, not a second architecture.**

Concretely: `signAsset()` gains a transport switch on `SCRUPLE_C2PA_SIGNER_URL`.

- **Unset** → today's behaviour, `spawn(sign.py)`, `asset_path` on the local filesystem. This is dev mode and it stays.
- **Set** → POST `multipart/form-data` to `${SCRUPLE_C2PA_SIGNER_URL}/sign` with the asset bytes as one part and the job spec JSON as another; receive signed bytes back.

The job spec is byte-identical between the two transports. That is the property worth protecting: one manifest builder, one assertion contract, one partition enforcement, two ways of moving bytes.

**And the caller changes shape.** `POST /api/scruple/c2pa/sign` should stop taking `asset_path` from clients. Studio does not have one and never will — the browser holds no filesystem path, the Modal container's paths are meaningless to the app host, and the desktop plugins cannot supply one either. Replace it with:

```
{ project_id, iteration_id, product, tier, title?,
  source: { kind: 'iteration' } | { kind: 'upload' } }
```

For `kind: 'iteration'` the route resolves bytes itself, in this order: local artifact (`readArtifact(output_hash)`), then the storage pointer via `provider.readFile`. It already has the row. For `kind: 'upload'` the request is `multipart/form-data` and the bytes come from the part — that is the desktop-plugin path and the one the runbook already documents.

`asset_path` stays accepted for one release **only when `SCRUPLE_C2PA_SIGNER_URL` is unset**, so `scripts/c2pa-sign.mjs` and `scripts/test-c2pa-sign-witness-e2e.ts` keep working. It is not part of the canon surface. Under `CANON_SKELETON.md` D-1 there are no production callers to protect.

One consequence to state plainly: `scripts/c2pa-sign.mjs:79-80` does `readFileSync(json.signed_path)` — it reads a path the *server* returned. That only works co-located, and the temp directory created at `route.ts:158` is **never cleaned up**. Under Option A the response should carry the signed bytes' hash and a retrieval URL, not a server-side path, and the signed derivative should be stored (§6, change 7) rather than orphaned in `/tmp`.

## 3. Which assertions should a Studio-signed manifest carry?

### 3a. What the allowlist permits today

`config/c2pa-assertions.json`, `created.application_tier`:

```
cawg.training-mining
ai.scruple.provenance
ai.scruple.workflow
ai.scruple.cad
```

Matching is version-insensitive — `assertion_partition.py:90-99` strips a trailing `.vN`, and `signAsset.ts:209-211` mirrors it. **`ai.scruple.workflow` is already on the allowlist.** I ran the real partitioner against a Studio-shaped assertion set:

```
partition audit: {"created_count": 3, "gathered_count": 0, "rejected_count": 0,
 "created_labels": ["cawg.training-mining", "ai.scruple.provenance.v1", "ai.scruple.workflow.v1"], ...}
```

So the base Studio manifest needs **no contract change**. That is a better starting position than Gap 1 implied.

### 3b. The measurement that decides how much to put in

I instrumented the ES256 callback and signed the same asset with the `ai.scruple.workflow.v1` payload padded to 0, 8, 64 and 256 KiB:

```
assertion payload +0 KiB   -> TBS bytes 1931
assertion payload +8 KiB   -> TBS bytes 1931
assertion payload +64 KiB  -> TBS bytes 1931
assertion payload +256 KiB -> TBS bytes 1931
```

The to-be-signed COSE structure is **constant** — the claim carries hashed URIs, not assertion bytes. Two conclusions:

- Assertion size does not threaten OCI KMS's RAW-message limit. `vault_sign.py:76-89` always sends `messageType="RAW"`; at ~1.9 KB plus ~100 bytes per additional hashed URI, there is comfortable headroom. *(That the real KMS RAW limit is 4 KB is from memory and is **UNVERIFIED** here — but the margin is large enough that it does not drive the design.)*
- Therefore the argument against embedding the full workflow graph is **not** a size argument. It is a disclosure argument, and it is `workflow_publication`.

### 3c. What belongs, and under which label

**`ai.scruple.provenance.v1`** — unchanged shape (`signAsset.ts:25-40`, built at `route.ts:86-104`). Carries `lock_tier`, `scr_id`, `leaf_hash`, `merkle_root`, `chain_position`, `signed_at`, and tier-gated lock/chain fields. This is the Scruple-side identity of the event and it is the natural home for the leaf reference (§4).

**`ai.scruple.workflow.v1`** — the Studio assertion. `WorkflowAssertionData` (`signAsset.ts:42-49`) already declares exactly the right fields and every one of them is a hash:

| Field | Source | Present on the proxy path today? |
|---|---|---|
| `workflow_hash` | `iterations.workflow_hash` (`ingest.ts:207`) | **yes** |
| `model_fingerprints_hash` | `iterations.model_fingerprints_hash` (`ingest.ts:220`) | no — needs the change in §6.1 |
| `machine_manifest_hash` | `iterations.machine_manifest_hash` | yes, but descriptor-only (Headline 3) |
| `prompt_hash` | not stored; derive `sha256(iterations.prompt)` | derivable |
| `seed` | not extracted from the graph | no |
| `generation_type` | derive from `output_kind` + graph node classes | derivable |

**Add two fields to this assertion, and one field to say what was disclosed:**

- `input_hash` — `iterations.input_hash` (`ingest.ts:196`). It is a first-class component of the leaf preimage and its absence from the manifest means a verifier reading only the C2PA credential cannot re-derive the leaf.
- `leaf_scheme` — `'v1' | 'v2' | 'v2.2'`. Without it a verifier does not know which preimage recipe to use, and `v1` means *the witness was unreachable and this hash is just the output hash*. Signing a `v1` iteration without saying so is the same class of error as `/v2/verify` reading the HMAC column.
- `disclosure` — `'full' | 'hash-only' | 'witness-only'`, from `iterations.workflow_publication`.

That last one is not decoration. `app/receipt/[scrId]/page.tsx:376-382` treats publication mode as **presentation only** — "The leaf preimage always commits everything; this is presentation only." That is fine for a web page the user can re-render. A C2PA manifest is an exported, permanently-attached artifact. If a user has set `hash-only`, a manifest that leaks the graph is an irreversible disclosure, and `app/api/iterations/[id]/publication/route.ts:22-26` makes publication mode **upgrade-only** precisely because disclosure cannot be undone. So:

- `witness-only` → emit `workflow_hash` only.
- `hash-only` → emit all the hashes above. **This is the default and the recommended maximum.**
- `full` → the same, *plus* optionally the graph itself under a separate label (below).

**Do NOT put the ComfyUI graph inside `ai.scruple.workflow.v1`.** Keep that assertion a fixed-size, all-hashes record. If the raw graph is ever emitted, it belongs in its own label so a consumer can drop it without losing the provenance record, and so the allowlist decision is made once, explicitly:

- **`ai.scruple.workflow-graph.v1`** — the canonical workflow JSON, emitted **only** when `workflow_publication === 'full'`. **This label is not on the allowlist and signing will refuse until it is added to `created.application_tier`.**

**`ai.scruple.machine.v1`** — *(new label, also requires an allowlist addition)* the container manifest from `modal/container_manifest.py:139-159`: `comfyui_version`, `comfyui_commit_sha`, and `custom_nodes[] = {pack, commit_sha, contents_hash}`. This is the assertion that makes the git-SHA claim real rather than aspirational, and it is the one genuinely distinctive thing Studio has. It should carry a `source` discriminator with two values — `'container'` when it came from `container_machine_manifest_hash`, `'descriptor'` when it fell back to `machines.manifest_hash` — because a descriptor with six `commit_sha: null` entries and three `main` refs pins nothing, and a manifest that presents both identically would be making the §12.4 mistake in a new place.

I would **defer** this label rather than ship it half-true. Emit it only when `containerMachineManifest` is actually present, which requires the §6.1 plumbing fix first. Until then, `machine_manifest_hash` inside `ai.scruple.workflow.v1` is honest as a bare hash.

**Gathered, not created.** Nothing in Studio's capture originates outside the TOE — the proxy sees the bytes server-side by construction (`lib/canvas/witness.ts:9-14`). So Studio contributes **no** `gathered_assertions`. `GATHERED_ALLOWLIST` (`stds.schema-org.CreativeWork`, `stds.iptc`, `stds.exif`) stays untouched.

**`cawg.training-mining`** — already always emitted (`signAsset.ts:245-248`), `{entries:[{use:'notAllowed'}]}`. Keep. Given Studio has Kohya inside it, an opt-out asserted by a product that trains models is worth being deliberate about, but the current unconditional value is the defensible one.

**`c2pa.actions`** — the inception action comes from `set_intent`. Studio's default `digitalSourceType` should stay `TRAINED_ALGORITHMIC_MEDIA` for txt2img/txt2video, but **img2img and upscale are `COMPOSITE_WITH_TRAINED_ALGORITHMIC_MEDIA` or `ALGORITHMICALLY_ENHANCED`**, and the enum already exists (`signAsset.ts:67-75`). The route currently never sets it, so every Studio asset would claim pure GenAI provenance regardless of whether a human-supplied source image fed it. Derive it from `input_artifacts` kind: any `init_image`/`source_image`/`control_image` present → composite.

## 4. Should the manifest reference the Scruple leaf, and how?

**Yes, and it already partly does — in the weakest of the three available ways.**

`ScrupleAssertionData.leaf_hash` (`signAsset.ts:29`) is populated from `it?.leaf_hash` at `route.ts:89`. That is a **bare hex string in a Scruple-namespaced assertion**. A generic C2PA verifier sees an opaque blob. Standard §12.4's principle — stored must not read as verified — cuts here too: a hash a third party cannot resolve or check is a claim, not evidence.

Three mechanisms, and I recommend all three, because they serve different readers:

**(i) The assertion — keep it, and complete it.** Add alongside `leaf_hash`:

- `leaf_signature`, `leaf_signer_key_id`, `leaf_signature_alg` — the H-1 ECDSA fields that Phase 1 shows the witness returns and `ingest.ts:359-361` currently discards. **This is the whole point of the reference.** With them, a verifier holding the published KMS public key can check the leaf without contacting Scruple. Without them, the leaf reference is a lookup key into Scruple's database and nothing more.
- `receipt_url` — `/api/v2/receipt/<iteration_id>`, which is public and unauthenticated by design (`app/api/v2/receipt/[leaf_id]/route.ts:1-9`).
- `verify_url` — `/api/v2/verify/<output_hash>`.
- `witness_key_url` — where the verifying key is published, so the signature is checkable without Scruple's cooperation. This is the field that turns the reference from a claim into evidence.

**This creates an ordering constraint that governs the whole design: the leaf must be signed before the manifest is.** Which means Phase 1 (leaf signature) is a hard prerequisite for Phase 3, not merely a cheaper win to do first. If C2PA ships before H-1, every Studio manifest carries a leaf reference whose only backing is an HMAC Scruple can forge — a content credential asserting, at C2PA Level 2, a provenance chain that terminates in a symmetric secret. That is the `L2_FLOOR.md` §1 inversion reproduced inside the C2PA modality itself, and it would be considerably harder to walk back than the current silence.

**(ii) A C2PA ingredient, for the master→derivative relation.** Migration `038_watermark_derivative.sql:5-9` already prescribes this: *"Derivative bytes get their own hash, own signed C2PA manifest, own witness leaf, and reference the master via a `c2pa.actions.v2` `c2pa.edited` action + ingredient."* `Builder.add_ingredient` and `add_ingredient_from_stream` exist in c2pa 0.36. When Phase 2's watermarking lands and the signed asset is a watermarked derivative, the clean master must appear as an ingredient with its own `leaf_hash`. This is how the two phases meet, and it is the one place where a *C2PA-native* mechanism expresses a Scruple relation, so a generic verifier sees the lineage without understanding `ai.scruple.*`.

**(iii) `claim_generator_info`.** Leave alone. `sign.py:202-210` correctly appends the real SDK version. Do not stuff Scruple identifiers here.

**One thing not to do:** do not make the leaf reference a *remote manifest* URL (`Builder.set_remote_url`). A content credential whose provenance is a live HTTP fetch against Scruple is precisely the "verifiable only with the issuer's cooperation" shape the receipt route's own header comment rejects.

## 5. Where in the flow does signing happen, and is it automatic or explicit?

### 5a. The candidate points

`/prompt` completion is wrong for the same reasons Phase 2 rejected watermarking at generation, plus two of its own.

Phase 2's §5b argument transfers intact: Studio's canonical loop is generate → feed back as img2img/ControlNet input → or into a Kohya LoRA training set. Signing at `/prompt` would mean the graph's own outputs re-enter as C2PA-bearing ingredients, and `/view` is how ComfyUI renders its **own thumbnails** (`app/canvas-proxy/…/route.ts:70-73` acknowledges this), so every preview refresh would trigger a sign. An artist generating fifty images and keeping two would produce fifty signed manifests, forty-eight of which are for images that were never published.

Two more specific to C2PA:

- **The tier does not exist yet.** `tierRequirementsMet` (`route.ts:62-77`) needs `scr_id`, or `lock_server_signature`, or `rvn_txid`. At `/prompt` completion the project has none. Only `bare` would ever pass — and `bare` suppresses `ai.scruple.provenance` entirely (`signAsset.ts:251`). Automatic signing at generation could only ever produce the tier that carries no Scruple provenance at all.
- **The leaf does not exist yet.** The reference in §4 is to a leaf produced by `ingestIteration`, which runs *after* the bytes are captured.

`captureOutput` is also wrong, and for a reason that is specifically C2PA's: **C2PA signing changes the bytes.** `ingest.ts:146` hashes `p.imageBytes` and that hash goes to the witness as `contentHash` (294-303). Sign before that and the leaf commits the *signed* bytes, which means the manifest must contain the leaf hash of a file the manifest is inside — a circularity with no resolution. Sign after and the leaf commits the unsigned master, which is correct and is what should happen.

### 5b. Recommendation

**Explicit, at publication time, in the same place and the same order Phase 2 puts watermarking — and after it.**

The sequence inside a lock route, extending Phase 2's §5e ordering:

```
1.  build Merkle over the master leaves
2.  derive the tier's watermark payload
3.  embed  → derivative bytes → derivative_hash
4.  WITNESS the derivative leaf                        ← project still unlocked
5.  persist watermark_derivative_leaf_hash
5b. C2PA-SIGN the derivative                           ← NEW
      ingredient  = the clean master + its leaf_hash
      assertions  = provenance(derivative leaf) + workflow + machine
      → c2pa_asset_hash, c2pa_manifest_hash
5c. WITNESS the signed asset as a third leaf           ← NEW, and see below
6.  rebuild the Merkle over master + derivative + signed leaves
7.  confirmAndExecute('finalize' | 'chain-lock-*')     ← seals the project last
```

Two notes on step 5c. First, the C2PA sign event **already** produces a leaf — `emitC2paSignLeaf` on the internal `scruple.c2pa.sign` stream (`route.ts:190-200`). That is a Scruple-internal audit record on tenant `TEN_scruple`, not a leaf on the user's project chain, and it should stay that way. Step 5c is about the *user's* chain committing the bytes they will actually distribute. Second, this is a third generation of the same file, and there is a defensible simpler answer: sign the derivative and record `c2pa_asset_hash` on the derivative's row without minting a third leaf, accepting that the distributed file's exact bytes are committed by the C2PA signature rather than by a witness leaf. That is weaker but it is not dishonest, because the C2PA signature *is* an ECDSA signature by the same key. **I would ship the simpler form first** and treat the third leaf as the stated end state, for the same reason Phase 2 recommends (i)-now/(ii)-later on the SCR_ID circularity.

**Automatic within a modality selection; never automatic without one.** The user's choice is `modalities: ['c2pa', …]` on `POST /api/v2/mark`, which `CANON_SKELETON.md` D-4/D-5 already establish and migration 039 already has columns for. Once selected, signing happens without a second call. This is exactly the shape D-6 gives chain-lock + watermark, and it is what stops the C2PA control from being a fifth broken button.

**Fail-closed, and say which.** `app/api/v2/mark/route.ts:106-113` currently reports `c2pa` as outstanding with a good reason. When the signer is reachable that branch becomes a real call; when it is not, it must keep reporting outstanding rather than degrading. `route.ts:86-95` already fails closed on an inapplicable MIME — keep that, and note it catches a real Studio case: **`video/webm` is not in `C2PA_SIGNABLE`** (`lib/v2/capabilities.ts:39-45`), is not in `formats.GENERATE_MIMES`, and is not in `Builder.get_supported_mime_types()` on c2pa 0.36. Studio produces webm (`lib/canvas/witness.ts:104-105`, and the runner's `SaveWEBM` branch). A user who selects C2PA on a webm output gets a correct 4xx today — that behaviour must survive, because the alternative is a silent skip.

### 7.8 What the surrogate cannot tell you here

Beyond the four items in `services/cvm-surrogate/README.md`, one more is specific to C2PA: **the surrogate says nothing about the certificate**. C2PA validity depends on a cert chain issued by a CA in the C2PA trust list; the surrogate signs with a key whose chain is `Scruple Dev Root CA … FOR TESTING_ONLY`. Every asset produced by this procedure is `Valid` only under `verify_trust: False`. Real trust-list validation is a CA question (`oci-console-walkthrough.md` Phase 8: "Wait for the CA (days to weeks)"), not a CVM question, and no amount of surrogate work advances it.
