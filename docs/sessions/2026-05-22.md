## The bug behind CAP-6

`modal/scruple_runner.py` `run_workflow` polled ComfyUI `/history` and
**only broke the loop when `hist[prompt_id]["outputs"]` was non-empty**.
`SaveImage` / `SaveVideo` register entries under `outputs` → image/video
workflows broke and worked. `SaveLoRA` / `TrainLoraNode` /
`CheckpointSave` are terminal nodes that write a `.safetensors` straight
to disk and **register no `/view` output**. The loop spun the full 1700s
on every checkpoint workflow even though the prompt finished in
seconds.

Symptoms previously misdiagnosed as GPU preemption, slow training,
and queue contention.

**Fix:** break on ComfyUI's real done-signal
(`status.completed` / `status_str=='success'`), then collect the
disk-written `.safetensors` for training runs. Plus `_tail_comfy_log()`
so error/timeout returns now carry the ComfyUI log tail — the
instrumentation whose absence hid this for so long.

**Result:** CAP-6 proven in 39s (cold) / 21–24s (warm) per LoRA
checkpoint on A10G. Three checkpoints (sd15lora_b/c/d, ranks 4/8/16)
witnessed end-to-end on project 13.

> Lesson: when ComfyUI runs "forever," get `/tmp/comfyui.log` from the
> container before theorizing about infra. The poll-loop completion
> check belongs to the workflow contract, not the runner.

RVN-anchored Merkle could actually cover:

- **T6** — no anchor until lock. **Acknowledged**; out of scope this session.
- **T7** — witness log not hash-chained. **Closed in v2** via `prev_record_hash`.
- **T8** — co-located trust. Inherent to a reference impl.
- **T9/T10** — input authenticity / storage drift. Low-priority.
- **T11** — "each step" not captured. **Partially closed via M-series** (model fingerprinting).
- **T12** — secret hygiene.

The user corrected my initial "HMAC is vestigial" framing, sharpening
the model: HMAC is the per-record seal *inside* the package; the on-chain
RVN mint by Scruple's known wallet is the public issuer identity. Together
they give outsiders end-to-end veracity. This reframe made T3 the
load-bearing fix and made T5 a non-concern for web.

## W-series — v2 full-record leaf

**Protocol change.** Canonical record gains `input_hash`, `workflow_hash`,
`prev_record_hash` between the basic fields. `leaf = sha256(canonical(record))`.

```
v1:  leaf_hash == output_hash
v2:  record = { run_sequence, output_hash, input_hash, workflow_hash,
                server_timestamp, prev_record_hash }
     leaf   = sha256(canonical(record))
```

The on-chain Merkle root now commits the full provenance package, not
just outputs. Verifier proves "this exact recipe + inputs produced this
output in this order at this time" — not just "this output existed."

**Canonicalization gotcha** caught by the audit: Python's `json.dumps`
defaults to `ensure_ascii=True` (escapes em-dash as `—`), Node's
`JSON.stringify` emits literal UTF-8. Initial audit returned 128/133
because prompts contained `—`. Fixed by `ensure_ascii=False` in the
Python reference; receipt's verification recipe now documents the rule
explicitly so external verifiers in any language don't trip on it.

**Web-only rollout decided.** Desktop still emits v1 leaves; reconcile
when desktop is next touched.

**Verified E2E** with all 5 modes (img2img, txt2img, txt2vid, img2vid,
training). 286/286 audit pass.

## Persistent chain lock for all 5 modes

Created 5 fresh projects (one per mode), chain-locked pinned tier via
wallet path. Discovered **two real bugs** along the way:

1. `witness.lockProject` wasn't forwarding `tier` → witness's
   `handleLock` defaulted to `basic` → IPFS never pinned. Pinned tier
   was unreachable from wallet mode.
2. `/api/lock/chain` Path B captured ipfs/arweave only from the Stripe
   `exec` result, not from the wallet `lock` response. Even if witness
   anchored both, the web side wrote NULL.
3. Receipt regex was `[A-F0-9]{6}` but chain lock derives `SCR_<8 hex>`
   (local lock is 6). All 5 fresh chain receipts 404'd until I
   relaxed to `{6,8}`.

All fixed in `ddb059f`. **286 → 307 → 286/307**(?) — final pass was 286/286 on the original local-locked 5 + 30 new chain-anchor checks per chain project = **286/286 across 10 projects** (5 local + 5 chain).

## M-series — model fingerprinting (v2.1)

User asked: in our shared-volume Modal config, could a user bait-and-switch
a model file? Answer: yes, **and** the v2 leaf doesn't catch it because
`workflow_hash` binds only the workflow JSON string (`ckpt_name:
"v1-5-..."`), not the actual weight bytes.

User's reframe of the fix: "we don't need to prevent the swap, we need
to hash the file the user uploads. If they later claim to use a
different file, the original hash-on-load won't match." That's exactly
what's needed — provenance is honest about what was loaded; verifiers
detect any later swap by re-hashing.

**Protocol bump to v2.1.** New field `model_fingerprints_hash` folded
between `workflow_hash` and `server_timestamp`:

```
v2.1:  record = { run_sequence, output_hash, input_hash, workflow_hash,
                  model_fingerprints_hash,
                  server_timestamp, prev_record_hash }
       leaf   = sha256(canonical(record))
```

Inside the Modal container, `_hash_workflow_models()` walks the
workflow for known loader nodes, hashes each file on the volume
(chunked sha256 + safetensors header sha256), returns a manifest
keyed by `<subdir>/<filename>`. Cache by `(path, mtime_ns, size)` so a
canonical 4.27 GB SD1.5 hashes once per warm container.

**Audit-script backward compatibility.** v2.0 leaves (pre-017) have no
`model_fingerprints_hash` field; the script tries v2.1 first, falls back
to v2.0. Reports protocol version per leaf.

**Bonus finding worth flagging:** the SD1.5 file on our Modal volume
hashes to `6ce0161689b3853acaa03779ec93eafe75a02f4ced659bee03f50797806fa2fa`
— **not** HuggingFace's official RunwayML hash `cc6cb27103...`. The
file is either a re-pruned copy, a different upload, or someone wrote
non-canonical bytes earlier. Provenance is now honest about exactly
that; whether to replace the volume copy with canonical is a product
decision. The canonical-hash registry (still TODO) would have flagged
this at upload time.

## L-series — kill the dev bypass

`/api/lock/checkpoint` and `/api/lock/local` had a `LOCK_REQUIRE_PAYMENT`
env + a `if (false && ...)` dead branch that made `paymentIntentId`
optional and skipped the witness server entirely when absent. We'd been
leaning on this dev-bypass for all CLI testing.

User's correction: "dev mode is a login-gated function. I login either
from the server with ssh, or with a dev google account, which we log
here on the server." Then: "the only difference between dev mode and
production is the test nets."

So the right architecture is:
- One codebase, one code path.
- Dev deployment points the same code at sandbox endpoints (sk_test,
  RVN testnet, arlocal, Kubo).
- Identity gate (`SCRUPLE_ALLOWED_EMAILS`) determines who can sign in on
  which deployment. SSH-originated CLI uses the existing `/api/dev/session`
  (shared-secret gated).

**Cleanup shipped:**
- Identity gate in `lib/auth/auth.ts` — `signIn` callback rejects non-whitelisted Google accounts.
- Dropped `LOCK_REQUIRE_PAYMENT` + dev-bypass branches from both lock routes.
- `paymentIntentId` is now required everywhere.
- Witness's `handleConfirmAndExecute` now signs both finalize AND checkpoint over `{ project_id, action, merkle_root, witnessed_count, locked_at }` (action in tuple → no signature replay across actions). Returns `serverSignature`.
- Web persists the witness countersignature in `projects.lock_server_signature` + `projects.lock_locked_at_witnessed` (migration 018). Receipt renders the new "Lock countersignature" section.

**Pre-existing bug surfaced and fixed:** `/api/stripe/payment-intent` was
namespacing the project id as `sw:<userId>:<id>` while every other web
caller passed bare ids. The witness's anti-tamper check
(`metadata.projectId === request.projectId`) was structurally going to
fail on real round-trip. Means the pre-existing Stripe-paid chain-lock
path was broken — only wallet-mode chain locks were actually working.
Aligned to bare ids.

**CLI test harness for paid flows** (so we never need the bypass back):
- `scripts/stripe-test-pay.mjs` — creates a sandbox PI, confirms with
  `pm_card_visa` via the new loopback-only `/api/admin/confirm-pi` on
  the witness server. Prints `PAYMENT_INTENT=<id>`.
- `scripts/scruple-run.ts --lock <action>` — one CLI invocation drives
  capture → test-pay → lock.

**Smoke validated** with project 25 (v2-paid-flow-smoke): capture +
paid checkpoint (sig `449a575cd2e2…`) + paid local lock (sig
`ebb986b1e2e6…`, different — action in tuple). Both persisted on the
project row.
